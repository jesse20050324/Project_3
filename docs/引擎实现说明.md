## 二、数据流

```
第五幕-上线定稿.yaml       ──┐
tools/ch5-timing.yaml (overlay) ──┼→ tools/build-chapter.mjs → content/chapter-05.yaml
                                 │                                   │
content/chapter-01/03/04.yaml ────┴───────────────────────────────────┤
                                                                       ↓
                                                        loadScript.ts（严格解析）
                                                                       ↓
                                                        timeline.ts（排序键、门、索引）
                                                          ↓          ↓
                                                     scheduler.ts  simulate.ts
                                                          ↓
                                                     reducer.ts / storage.ts (v2)
                                                          ↓

                                                          ↓

```

`timeline.ts` 是**唯一排序真相**：运行时调度与穷举仿真读同一份 `sortKey` / `beatById` / `orderedBeats`，杜绝「出图一套顺序、播放另一套顺序」。

## 三、生成器

```bash
node tools/build-chapter.mjs          # 重出 content/chapter-05.yaml
node tools/build-chapter.mjs --check  # 不写盘，只比对生成物是否已与定稿同步
```

单向映射（正文逐字搬运，不改写）：

| 定稿源 | 实现层 |
|---|---|
| ① 用户消息 | `lines` 里角色台词 |
| ② AI 思考 | `from: ai` + `delivery: thought` |
| ③ 选项 | `choices[].thought` |
| ④ AI 回复 | `choices[].reply` |
| `分叉` | 多个 `choices[].next`（各自独立分支拍，之后汇合） |
| `下一` | `next` |
| `等待` | `requires`（严格等待门） |
| `时间` + 顶层 `时间轴` | 每拍 `time`、`timeRank`；章顶层 `时间轴` |
| `入场` | `when` 旗标（三种入场变体互斥） |
| `终局` | `ending` + 章顶层 `endings` 双窗共同抵达声明 |
| `记忆候选` | `记忆候选`（四格全名）保留 |

两窗同号拍按 `所属` 加 `5m.` / `5f.` 前缀，保证 id 全局唯一。生成器先校验定稿源结构（章号=5、时间轴无重复、轮次非空），任何字段走样直接停下。`--check` 由 `scriptSync.test.ts` 调用，是该测试的核心断言。

**调参入口 `tools/ch5-timing.yaml`**：

- `标题`、`默认节拍`：章级信息；
- `入场旗标`：定稿三种入场文字 → 引擎 `when` 旗标（幕4 4.2.2 / 4.3.3 设置的 `男生意向`/`女生意向`）；
- `拍序`：全局播出顺序，第五章显式写 `order`，由时间轴 16 档＋共享事件因果推得；
- `区间`：3 组自然语言「节拍对位」→ 机器可读 `window`；
- `清空教学记忆`：给 6 个入场变体拍注入 `清空记忆`（v5.1 定稿没有这个字段，属实现层世界观约定）；
- `终局`：「在一起」需要 `5m.4.4` 与 `5f.4.4` 双窗共同抵达；
- `节拍`：逐消息节拍覆盖，见第八节。

## 四、字段契约

顶层：`title`、`chapter`、`时间轴`、`默认节拍`、`speakers`、`endings`、`beats`。

`beats[]`：`id`、`channel`、`label`、`time`、`timeRank`、`order`、`when`、`requires`、`window`、`清空记忆`、`记忆候选`、`节拍`、`ending`、`lines`、`choices`、`next`。

`lines[]`：`from`、`text`、`delivery`（`type` / `pop` / `image` / `thought`）、`节拍`。
`choices[]`：`thought`、`reply`、`set`、`需记忆`、`next`、`节拍`。

`loadScript.ts` **遇到未声明字段即报错**，并列出文件、拍 id 与字段名——这是为了杜绝「剧本加了字段、引擎静默丢弃」这类历史漂移。新增字段必须同时更新 `types.ts`、`loadScript.ts`、`validate.ts` 与本文。

`validate.ts` 启动校验：id 重复、引用不存在、`next` 跨侧、`requires` 成环、孤立拍、时间轴一致性、区间端点合法性与章内先后、终局声明与双窗配对、节拍数值范围（0~20000ms）、记忆候选短句逐字出现。

## 五、三类跨窗时序

| 类型 | 字段 | 语义 |
|---|---|---|
| 严格等待 | `requires: [对侧拍 id…]` | 列出的拍全部完成才放行，先后固定 |
| 区间包含 | `window: { channel, 下界: [...], 上界: [...], 说明 }` | 下界中至少一拍已完成 → 开门；上界中任一拍已完成 → 关门。区间内两窗谁先谁后无所谓；关门时本拍仍未播 = 顺序反了 |
| 同段自由 | 无门 | 同档拍按全局排序键先后播，不看消息历史最后一条在哪一侧 |

`windowState()` 返回 `none | waiting | open | closed`；`windowViolation()` 生成可行动报错（含拍 id 与越界的上界拍），供仿真、reducer 的 `state.error` 与运行时校验使用。

第五章上线稿有 9 个 `requires`、11 个区间拍、16 档时间轴。拍序和区间以 `tools/ch5-timing.yaml` 为准。

## 六、排序与调度状态机

- `assignSchedule(script)` 在加载期一次性算 `sortKey = chapter × 10^6 + order`（`order` 缺省按文件顺序）、`timeRank`（取 `时间轴` 下标），并预建 `beatById` / `orderedBeats`。运行时 `availableBeat()` 只遍历已激活候选，不再每帧 `beats.find`。
- `compareBeats()` 排序键相同时用 id 做稳定兜底。
- `playbackStep()` 取排序键最小的可播拍。v0.6.1 起，两窗没有全局忙锁。同一时间档或早期无依赖的拍可以并播；第五幕起跨时间档仍守前后，区间上界等待已激活的区间拍完成。
- **`commitLine` / `commitReply` 播完只 `completeBeat()`，不自动接下一拍**。旧实现的这条局部旁路会让一条线一路播到底，是「女线 16 拍全部播不到」与「区间被提前关掉」的根因。
- 网状结构继续用 `activated` / `completed` 有向图模型：它本就支持多入口、多分支与汇合，只需补齐 `ending` 与双窗共同置旗。
- 异常不再被 reducer 静默吞掉：写入 `state.error`，由 `useEngine.ts` 在控制台输出（界面不展示调试信息），控制台不打印大段台词。

`src/engine/simulate.ts` 是无 React 的纯函数穷举：遍历入场旗标组合与所有 `choices` 组合，驱动 reducer，断言每拍可达、无区间越界、无死锁、终局可抵达、章切换不中断，并带路径上限保护。双窗同时停在选项时固定左→右解决，签名只保留 `requires`／区间上下界／终局／记忆门等后续决策相关字段，避免状态爆炸。实测第五章 40 拍全覆盖。

## 七、章状态机与存档 v2

`chapter`、`ritual`、`endings`、`error`、`runId` 全部在 `EngineState` 里并持久化（`shuangxian.progress.v2`）。跨章由 reducer 一步完成「切章 → 清该窗消息 → 记录仪式起点」，`ritualTick()` 幂等推进 mask→pause→clear；UI 只读持久化状态显示蒙版与结束动作。

这是「章节之间必须刷新才能继续」的根治：旧实现用 React 局部 `resetting`＋`ChatPane` 的 `setTimeout`，并从 `state.messages` 反推章号，刷新／StrictMode 双调用都会失同步。相应兼容补丁（`withMissingRoots`、`sync-roots`、`epoch` 换 key 重挂载）的运行时职责已移除，只在 storage 迁移里保留一次性旧档处理。

v1 旧档不静默清档：给出「剧本已更新，进度需重新开始」的明确提示后重置。缺字段由 `storage.ts` 归一化补齐。存档只存必需状态，不存派生索引。

## 八、逐消息节拍

设计取舍：**全局预设 ＋ 拍级默认 ＋ 逐句覆盖**三层，而不是把四个数字硬绑到每条消息上。剧本大部分消息应保持统一节奏，逐条写数字会污染 YAML；但情绪钩子、慢回、长停顿必须能单独强调。

```ts
type Timing = { pauseBeforeMs; indicatorMs; typeIntervalMs; afterMs };
```

- 全局预设 `src/presentation.ts` 的 `PACING`：`极快`(0/280/40/220)、`快`、`正常`(240/1000/100/900)、`慢`、`长停顿`(1700/2100/165/2100)。**整体调改这里一处**。
- 章默认 `默认节拍`、拍默认 `beat.节拍`、逐句 `line.节拍` / `choice.节拍`。预设名整份替换，数值对象逐字段覆盖；`resolveTiming(chain)` 按从宽到窄叠加，产出一个已定值对象挂到 `ChatMessage.timing`，UI 直接读、不重复计算。
- 第五章的覆盖写在 `tools/ch5-timing.yaml` 的 `节拍.拍`（键为引擎 id）、`节拍.句`（`id:行号`，0=①用户消息，1=②AI思考）、`节拍.选项`（`id:选项号`）。**单句调改 overlay 一行**，改完重跑生成器＋`--check`。
- `pacingError()` 校验预设名与数值范围（0~20000ms）；`prefers-reduced-motion` 时 `resolveTiming` 返回 `ZERO_TIMING`，全部归零。
- `ChatPane` 按 `pause → indicator → typing/shown → afterMs → commit` 驱动，计时器随 `Timing` 变化正确清理。旧常量 `TYPE_INTERVAL_MS` / `AFTER_TYPE_MS` / `INDICATOR_MS` 降级为「正常」预设兜底，向后兼容 CH1/3/4。
- **界面不提供调速控件**（v0.4.1 起废除）：全部调参都在预设文件或 overlay 里完成，`ChatPane` 只消费已定值，减少动态效果时归零。

## 九、界面

按只读的双线 UI 模板重做：1440×920 固定画布＋窗口不足时整块等比缩放，不做响应式；用户消息左灰泡、AI 消息右纯文字（无头像/名字/气泡）；思考块在输入卡上方；胶囊想法选中即发送；输入卡 `active` / `locked` / `empty` 三态；三点打字态；确认重来弹层；无任何解释玩法文案。顶栏标题是正式游戏名 `He said, she said · 第N幕`，只有「重新开始」一个操作。token 来源与取舍见 [`界面设计背景.md`](界面设计背景.md)。零新增依赖：头像 base64 内联（`src/assets/avatars.ts`），图标内联 SVG（`src/components/icons.tsx`），不用 emoji、图标字体或外部 CDN。

**单窗浮层必须限定在窗内**：跨章蒙版 `.ritual-mask` 与记忆弹层 `.memory-dialog` 都是 `position: absolute; inset: 0`，因此 `.pane` 必须保持 `position: relative`。`.game-canvas` 带 `transform: scale()` 会创建 containing block，若 `.pane` 不是定位上下文，蒙版就会铺满整块 1440×920 画布，看起来像「全局重置」；逻辑层 `state.ritual[channel]` 本来就是分侧的。`Game.test.tsx` 同时锁住 DOM 分侧契约与这条 CSS 契约。

`App.tsx` 只有两个分支：剧本加载失败的错误页（`data-testid="script-error"`，用 `.script-error` 样式，不是调试 UI）与 `<Game>`。剧本加载期错误同时写 `console.error`。

> **v0.4.1 废案结论**：独立的结构/时序页面 `src/ScriptMap.tsx`、游戏内调试条 `src/components/DebugStrip.tsx`、顶栏「结构」「调试」入口、速度倍率按钮与 `#map` hash 路由**已全部删除**，该设计判定为废案、不再恢复。随之清理：只服务调试条的 `playerStatus` / `formatFlags` / `describeChannel` / `channelProgress` 与 `timeline.ts` 的 `progressOf` / `timeLabel`，`.debug-error` 样式，以及所有「调试视图用」注释。核心调度、仿真、区间门与三层节拍解析不受影响。

## 十一、已知取舍与边界

- 不为重构而重构：`activated`/`completed` 图模型、`choices[].next` 激活语义、`validate` 的记忆短句校验与严格等待、区间门都保留，只替换「靠消息到达顺序猜」的部分。
- 模板要求单文件零依赖，项目是 React/Vite，改为不新增依赖＋内联资源；模板要求固定画布不做响应式，照搬。
- 不为移动端做页签、不写解释性文案、不给 AI 加头像名字、不做真实输入框、不把结构图塞进游戏画面、**不提供任何调试类 UI**。
- 是否 push main 由用户决定（push 会触发 GitHub Pages 部署）。
- 第八章 `记忆后继` 按顺序匹配本窗记忆的 `{ all, next }` 条件；键盘和鼠标都使用引擎的同一判定。选定的后继随待播回复存档，刷新继续沿原后继。第七章完成后接第八章；只有实际结局才弹出最终提示并收录最后的双窗会话。

## 第六、七幕转换与播放

- `tools/build-later-chapters.mjs` 读已校验的审稿 Mermaid，生成 `content/chapter-06.yaml` 和 `content/chapter-07.yaml`。共同①②合为一拍，③④保留各自的选项、回复和后继。按日期和时间排序，以 `requires` 表达共享消息的发送先后。
- `control: true` 用于只承担时序或收束的无台词节点。周日路由根据已发送的消息旗标选择对侧看到的实际前情。记忆只有 `需记忆` 硬门，玩家点选后才发送对应回复。
- 第五幕起，另一窗较早的选择未完成时，较晚的拍等待。两个窗口可以分别开始重置，先完成重置的一窗仍遵守时序。第七幕换日显示日期分隔并保留本幕聊天。
- 记忆槽每窗五条，满槽替换在同一操作内完成。读入旧 v2 存档时只剔除第五幕已撤下的候选，保留游戏进度与其余记忆。第五幕正文仍由原生成链维护。
- 第五幕生成器和六七幕的源稿校验兼容 CRLF/LF。运行两个生成器的 `--check`，再运行 `npm test` 与 `npm run build`。完整依据见 [六七幕接入记录](剧本审稿/六七幕接入记录.md)。
