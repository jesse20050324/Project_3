## 系统上它实际是什么

它不是自由聊天，也不是传统文字冒险里「点一句台词就说出去」。更准确的结构是：

**两路并行的脚本对话 + 一个共享的状态黑板 + 一个聊天软件外壳。**

玩家不打字。每个选项是态度（客观分析、顺着说、压着反驳），选项背后绑着一条提前写好的回复、一组状态变化、以及接下来跳到哪一段。文档第 6 版已经把这个定下来了，我下面都按这个前提写。若其实还想让玩家自己打字，后面好几个模块都要改，这个问题我放在最后。

## 建议拆成的模块

按实现边界分成 9 块。原型期前 6 块就要有，后 3 块可以很薄，但数据格式上要留位，不然剧本一长就会返工。

**1. 聊天壳层**
左右两个对话窗（人数若改成 3，就是 N 个窗，不要写死成两个面板）。每条消息有发送者、所属对话、正文、呈现方式。还要有滚动、未读、头像或名字、以及「第二天」「三个月后」这种时间分隔。手机上两个窗放不下，所以要有切换，不能只做宽屏左右分栏。

**2. 演出调度**
同一条消息进窗口之前，先决定怎么出现：整条直接冒出来，或逐字打出；出现前可以有「正在输入」和一段停顿。播放期间锁住选择，避免玩家连点把队列打乱。文字速度以后会是个设置项，所以逐字播放要从第一天就做成可调的，而不是写死在动画里。

**3. 剧情运行时**
内容是一张图，不是一棵只能往下分叉、不能汇合的树。节点有几类：对方的一句或一组消息、玩家的态度选项、条件跳转、结局。一条边可以带条件（某旗标为真、好感大于某值）。两个窗口共用这一张图，每句台词标明出现在哪一边。

**4. 态度选项**
一个选项在数据上是两段文案，不要混成一段。玩家看到的是思考（「他现在其实在生气」），发出去的是写死的回复。选中后先播回复，再改状态，再走下一条边。

**5. 状态黑板**
后面所有分支都读这里。至少三种：

- 事件旗标：某件事发生过没有、某句话说过没有。
- 数值：关系紧绷度、某一侧对 AI 的信任，具体有几条等你定。
- 信息披露：对 A 说过什么、对 B 说过什么。双视角如果要有玩法，靠的就是这个，而不是再加一个好感数字。

**6. 两路对话怎么往下走**
这是架构上最容易走弯路的地方。建议用「节拍」，不要用「两条剧本各自自由跑、互相等旗标」。

一个节拍是作者排好的一小段：左边来几句，右边来几句，中间夹 0 到几次选择，播完才进入下一拍。下一拍能不能进，由黑板决定。这样写剧本的人控制顺序，程序只负责播放和判断。两条独立状态机互相等待，很容易死锁（A 等一个 B 永远不会设上的旗标），作者也很难看出当前卡在哪。

**7. 结局结算**
在少数关键节拍结尾看黑板，选出结局编号，再播结局对话。判断集中在这几个点上，不要散落在每一句台词里。

**8. 存档**
正式版要能中途退出。存「当前节拍 + 黑板 + 选过的选项」就够，聊天记录可以用这些重放出来，不必把每个气泡单独存一份。原型可以先做「重开这一章」。

**9. 内容格式**
台词、选项、条件、跳转要落在剧本数据里，不要写进界面代码。作者面对的应该是一份能看懂的剧本文本或表，程序只读这份数据。双视角会让字数大约翻倍，每个选项又是「思考 + 台词」两条，这一层比聊天界面更容易决定后面用什么工具。

## 玩家实际会碰到的一条流程

1. 当前节拍开始，调度器按作者写的顺序，往左或右窗口送消息。
2. 消息先显示「正在输入」，再整条弹出或逐字打出。
3. 遇到选项节点时，另一侧先停住。思考面板列出几个态度。
4. 玩家点一个态度。对应的固定回复在当前窗口播出来，黑板更新。
5. 节拍继续，直到这一拍结束。
6. 运行时看条件，进入下一拍，或者进入结局。

对方「会回复什么」全部来自剧本，没有实时生成。

## 有意先不做的

这些文档里没定，也不会改变上面的骨架，原型里不要提前做：自由输入、语音、表情包、立绘演出、多语言、成就、已读跳过、云存档。聊天头像可以后加，消息结构里留一个头像字段即可。

## 需要你定的事

前 4 个会改变系统形状，后几个只影响界面和内容量。

1. 玩家是不是永远不能自己打字，只能点态度？我目前按「只能点选」设计。
2. 两个窗口怎么推进？我建议作者排好顺序，两边按节拍交替往下播，玩家在指定位置选择。另一种是两边同时在等回复，玩家自己决定先回谁。第二种玩起来更像真的在用聊天软件，但剧本和程序都会难一截。
3. 选项里除了「对当前这个人的态度」，有没有「要不要把另一边刚说的事讲出去、用来劝人」？有的话，黑板里必须单独记信息披露；没有的话，双窗口主要是让玩家自己看见两边，选择仍然只影响当前这一条线。
4. 状态你希望细到什么程度？只有「发生过 / 没发生过」；加上每边一个好感或信任；还是还要关系紧绷度、某件事有没有被说破。
5. 原型的目标是一段完整的晚上（两边各若干轮，中间几次选择，至少两个不同后续），还是更短的技术切片（几个气泡加一次分支就行）？
6. 画面上除了文字，还要不要头像、图片、表情？时间跨度要不要在聊天记录里出现日期分隔？
7. 系统按固定 2 人做，还是按最多 3 个对话窗来留？
8. 谁来写台词、习惯改什么？纯文本、表格，还是节点图。这不决定引擎，但会决定剧情数据长什么样。

## 这类游戏实际用什么

界面长得像聊天软件的作品，几乎都没有用传统文字冒险那条「一次一句、点一下继续」的循环，而是自己画 UI，再用一套剧本数据驱动它。

| 作品 | 玩法上像我们的哪一块 | 技术 |
|---|---|---|
| [Bury me, my Love](https://www.thepixelhunt.com/blog_en/the-emotional-rollercoaster-of-making-a-video-game) | 聊天记录、点选回复、数值改结局、图片和表情 | MonoGame + [Ink](https://github.com/inkle/ink)。一条对话，不是两路并行。作者后来认为为了开源而避开 Unity，在工程上并不划算 |
| [Emily Is Away](https://handwiki.org/wiki/Software:Emily_Is_Away) | 仿老聊天软件，点选回复改关系 | Unity，自定义界面。主要是一个聊天窗 |
| [SIMULACRA](https://en.wikipedia.org/wiki/Simulacra_(video_game)) | 一部手机里多个联系人，一条聊天里得到的信息拿去推另一条 | 初代 libGDX，续作 Unity。这是已上线作品里最接近「多线互相解锁」的 |
| [Lifeline](https://www.gamedeveloper.com/design/building-a-narrative-out-of-push-notifications-in-i-lifeline-i-) | 来一条消息、做一个二选一、角色过一会再回 | 原型用 Twine 管分支，正式版是自己的引擎。单线，还带真实时间等待 |
| [Mystic Messenger](https://en.wikipedia.org/wiki/Mystic_Messenger) | 多个聊天室按好感和解锁 | 商业自研。解锁条件是「这个房间现在能不能进」，不是一句一句自由交错 |
| Ren'Py 上的 [Mysterious Messenger](https://github.com/shawna-p/mysterious-messenger) | 有人用文字冒险引擎硬做了整套手机 | 等于在 Ren'Py 里又写了一个引擎。社区里的手机界面方案也在绕开 NVL 模式，因为历史记录、头像、退出再进来会丢消息 |

共同的分层是三层，和上次列的模块对得上：

1. 剧本数据：谁说的、正文、选项、改哪些变量、下一拍去哪。
2. 运行时：变量、旗标、条件、当前走到哪。
3. 演出：气泡、逐字、整条弹出、正在输入、图片。剧本里用标签标记，不把界面写进句子里。

Ink 的官方用法就是这样。一行字后面可以挂 `#speaker:她 #delivery:type`，游戏读到标签再决定怎么播，标签本身不出现在气泡里。变量和条件放在剧本里，存档是整份故事状态导出成 JSON。

## 我们这个闸门，现成引擎并不直接提供

Ink 有一种叫 thread 的写法，它是把几段文案收进同一次选择，不是两个窗口各有一个进度条。另有一组仍标着测试阶段的 [多流程接口](https://github.com/inkle/ink/blob/master/Documentation/RunningYourInk.md)：一个故事里可以挂两条调用栈，变量共用，适合「主线说着话，旁边还有一段可以暂停的对话」。有人用它做过聊天侧线。它能表达两路进度，但「左边第 2 拍必须等右边第 3 拍」仍要写在外面：进这一拍之前先查依赖。

Yarn Spinner、Godot Dialogue Manager、Ren'Py 的 `label` 都是同一种形状：一次只跑一段对话。两路进度都是游戏自己的调度器，引擎只负责「给我下一段文案和选项」。

所以原型期更合适的数据是一拍一条，而不是先学一整套叙事语言。一拍大致长这样：

```yaml
id: L2
channel: left
requires: [R3]          # 没有这段就可以省略，左边就能连续往下聊
lines:
  - from: npc
    delivery: type      # type = 逐字，pop = 整条冒出
    text: 他今天一下午都没回我。
choices:
  - thought: 客观分析她现在的不安
    reply: 你在用「他没回」证明「他不在意」。这两件事不一定是一件事。
    set: { told_left_to_separate: true }
    next: L3a
  - thought: 顺着她的担心说
    reply: 如果你已经觉得被放着不管，这个感觉本身就是信息。
    set: { told_left_to_separate: false }
    next: L3b
```

调度规则就三条。某边的下一拍没有 `requires`，或依赖的拍已经播完，就可以播。正在播的时候锁住选择。加载剧本时如果发现环状等待，直接报错。

图片是这一拍里的另一种消息，`delivery: image` 加一个文件名，气泡里放图。原型放一张就能证明这条路通。

## 五条路

| 路 | 适合我们的程度 | 用 AI 做原型的速度 | 主要代价 |
|---|---|---|---|
| **网页：Vite + React + TypeScript，自写调度器** | 高。双窗、逐字、未读、窄屏改成切换，都是网页的日常界面 | 最快。改一句剧本，浏览器热更新就能看 | 没有现成的作家编辑器。以后要 Steam 安装包，再用 Tauri 包一层，故事数据不用重写 |
| 网页 + Ink | 中高。条件和变量很成熟，[inkjs](https://github.com/inkle/inkjs) 能在浏览器里跑 | 快，但每条内容多一次编译，闸门仍要自己写 | 多一套语言。多流程还是测试接口。你得先学 Ink 才能改剧本 |
| Ren'Py | 低到中。单线文字冒险、存档、回退很完整 | 慢。双窗要写成自定义屏幕，回退和存档容易跟聊天记录打架 | 社区有整套手机模板，说明做得到，也说明原生循环不够用 |
| Unity + Ink | 中。Emily Is Away、SIMULACRA 2 走的是这条 | 慢。同样一个气泡要场景、画布、预制体和 C# | 要做很重的演出、主机、复杂动画时再值得 |
| Godot + Dialogue Manager | 中。引擎比 Unity 轻，对话插件能做条件和变量 | 中等。界面仍要自己搭，脚本生态比 TypeScript 薄 | 和 Unity 一样，聊天窗不是它的默认形态 |

Pixi'VN 这类网页文字冒险库也看过。它强在立绘、文本框、存档，默认仍是「一次一句」。用它等于先接受文字冒险的播放方式，再拆掉。

## 为什么网页对这个项目更快

游戏画面就是一个聊天网站。React 做左右气泡、正在输入、逐字打出、点态度之后再播出写死的回复，是现成的界面模式。中文逐字就是按字切，没有引擎字体和编码问题。

剧本放在独立的 YAML 里，界面代码不碰台词。你可以自己改字，我改调度。热更新是改完刷新，不用进游戏编辑器点播放。

两条线的闸门可以用普通测试盖住：没有依赖时左边连走三拍；有依赖时左边停住；选项把后面带到两个不同的拍；两个拍互相等待时加载失败。这些坑在原型里就能碰到，不必先打开 Unity。

以后若要交给别人下载，同一份网页可以用 Tauri 打成桌面程序。已有用 Tauri 加 React 上 Steam 的游戏。itch.io 也可以直接传网页包。这条路不会把剧本锁死在某个引擎的脚本格式里。

Ren'Py 我写得出来，但双窗口的时间会花在屏幕语言、样式和回退上，而不是花在闸门上。官方文档写明，存档点落在脚本语句的开头，自定义屏幕中间的操作不容易存。Unity 同样能做，只是同样的界面步骤更多，对一个还在试玩法的原型不划算。

## 游戏里台词存在哪

存在一组文本文件里，一个人一个晚上可以是一个文件。里面不是一整篇文章，而是很多小段，每段有一个编号。段和段之间用「下一段是谁」连起来。

一段在文件里大概是这样：

```yaml
id: L2
channel: left
requires: [R1]
lines:
  - from: girl
    text: 他一下午都没回我。
choices:
  - thought: 客观分析
    reply: 没回消息，不等于不在意。
    set: { left_calm: true }
    next: L3a
  - thought: 顺着她说
    reply: 你已经觉得被忽略了。
    set: { left_calm: false }
    next: L3b
```

`thought` 是玩家点的那句思考，`reply` 是实际发出去的话。`set` 是这个选择改掉的旗标。`next` 是接下来播哪一段。`requires` 是闸门：这里要等右边的 `R1` 播完，左边才会出现这段。没有 `requires` 的段，左边可以连续往下聊，右边停着也没关系。

玩家看到的仍是两个聊天窗。这个文件只负责「有哪些话、哪句连哪句」。
