# 记忆系统实现方案（MVP 已落地版）

> 状态：教学闭环已实现并通过测试（2026-11-04）。本文记录数据模型、交互流、规则和与幕5正片规则的边界，供后续迭代与审阅。

## 一、设计依据（方法论速览）

- **阅后即焚**：AI 的聊天记录不自动保留，只有玩家主动存的记忆才留得住——玩家是 AI 的记忆管理者。
- **分窗独立**：记忆池按窗（男窗/女窗）分放、互不共享。跨窗共享等于 AI 把一扇窗里的话拿到另一扇窗当论据，破坏"两边互相看不到"的核心机制。
- **效果统一为置灰硬门**：记了能选、没记置灰，一眼可见；不做软性话术差异（软效果是否保留，待干扰项设计定稿后定）。
- 教学阶段：槽位数=候选数（无取舍），产出即用完，幕5 入场清零。

## 二、两个教学闭环

| 窗 | 存 | 用（置灰门） |
|---|---|---|
| 女窗 | CH1 R1 三变体：AI 报完地址后**女生复述一遍**（"OK，小寨华旗国际A座哈，你帮我记一下，我怕忘了"），候选挂她的复述行——记忆必须是角色说出的话，不是 AI 的话；她那句"你帮我记一下"也让存档动作在戏内成立 | CH3 3.4.1 地铁问路：「给出精确路线」需记忆「店的位置」；没存→置灰，只能「凭印象指一个」→ 吐槽拍 3.4.2 → 汇合 |
| 男窗 | CH3 3.2.2/3.3.1 的①里「好像是我妹的同桌还是什么」（候选「我妹的同桌」） | CH4 4.2.2 怂了拍：「让表妹帮忙牵线」需记忆「我妹的同桌」；没存→置灰（阅后即焚：AI 想不起那层关系），仍有「硬着头皮直接问」「先算了」两条路，全部收束到 问/不问 终局 |

## 三、数据模型（src/engine/types.ts）

```ts
// 节拍上的候选：可高亮存档的原文片段（①用户台词或④AI回复内）
type MemoryCandidate = { 缩略标签: string; 短句: string; 类型?: string; 线?: string };
// Choice 扩展：置灰门
type Choice = { thought; reply; set?; next?; 需记忆?: string };
// Beat 扩展
type Beat = { ...; 记忆候选?: MemoryCandidate[]; 清空记忆?: "all" | Channel };
// 运行时：已存记忆按窗分池
type MemoryEntry = { label: string; text: string; beatId: string };
type EngineState = { ...; memories: Record<Channel, MemoryEntry[]> };
```

- **保存**：`saveMemory(state, channel, entry)`——同缩略标签去重，只入本窗池（scheduler.ts）。
- **判定**：`hasMemory(state, channel, label)`——置灰门用。
- **拦截**：`choose()` 里对未满足 `需记忆` 的选项直接抛错（reducer 兜底；UI 层已置灰，正常点不到）。
- **清空**：`清空记忆` 指令在节拍完成时执行（`"all"` 或指定窗）——幕5 入场清教学记忆用。
- **校验**：validateScript 检查所有 `需记忆` 引用的标签必须有候选提供，否则剧本报错（防止永远选不了的选项）。
- **持久化**：EngineState 整体进 localStorage；旧存档无 memories 字段时补空池（storage.ts normalizeMemories）。

## 四、交互（最简版，动效后置）

- **高亮**：`MessageBubble` 渲染时，消息所属节拍的候选短句若出现在文本中 → 荧光笔高亮 span（`.memory-mark`，黄色荧光）；点击 → dispatch `save-memory`；已存的高亮淡化不可点（`.memory-mark-saved`）。正在打字的气泡不高亮，落定后出现。
- **计数入口**：每窗头部一个「记忆 x/x」按钮——x=已存数/已出现候选数。两个入口分窗，界面本身就是对话隔离的表达。
- **记忆窗**：点击入口打开浮层（backdrop 虚化、圆角卡），列出本窗记忆（缩略标签+原文）；空态提示"聊天里的高亮句子点一下就能存"。
- **置灰选项**：ChoicePanel 对 `需记忆` 未满足的选项渲染 disabled+提示「需要记忆：xx（还没存下这句）」。

## 五、剧本接口

- script 层字段（ch3/ch4/ch5 统一格式）：`记忆候选: {缩略标签,短句,类型,线}`、选项 `需记忆: 标签`、`清空记忆`。
- 引擎层（content/chapter-0N.yaml）：Beat 级 `记忆候选`、Choice 级 `需记忆`，js-yaml 直接透传，loadScript 显式解析。
- 候选来源：**一律来自角色台词（①）**——AI 自己说过的话不作为候选（店址经女生复述"你帮我记一下"转成她的话）；已由 validate 机器校验"短句必须一字不差出现在本拍台词或回复里"。
- 已撤候选（ARTX 太贵等）留在台词里作叙事纹理，不带候选注记。

## 六、与幕5 正片规则的边界（不在本 MVP 内）

1. **稀缺槽位**：幕5 起每窗槽位拟设 4~5（正牌 3+干扰 2），超槽需取舍；教学阶段不限。
2. **正牌/干扰体系**：钥匙（前期行为）/糖（前期理解）/自白（真实）三类正牌+生活趣闻干扰项，判定挂 8.5：认识到=持有本窗钥匙，缺则灰显提示；外归因永远可选。已按此模型写好 ch5.yaml，待接入引擎。
3. **清零**：幕5 入场拍需加 `清空记忆: all`（迁移 ch5 到引擎时落）。
4. **软效果**（记忆触发局部台词差异）是否保留：搁置，等干扰项定稿。
5. UI 升级项（飞行动画、神经网络布局、圆球）全部后置。

## 七、测试覆盖（story.test.ts "memory system"）

- 候选与门的配置正确性（标签互相引用成立）；
- 问路门：未存→精确路线 choose 抛错、凭印象可走通汇合；存后→精确路线解锁直跳 3.4.3；重复保存去重；
- 表妹门：未存→choose 抛错；直接问/先算了不受影响且正确 set 终局旗标；存后解锁并 set 男生意向=问；
- 清空指令：合成小剧本验证 `清空记忆: all` 在节拍完成后清两窗。

## 八、播控体验（串行节拍 + 章间重置）

- **串行节拍**（scheduler.canArm + ChatPane arm 门）：任何一窗只有在对面"完全结束"（不在播出 lines/reply；停在 choices 等玩家视为结束）后才开演；双方同时就绪时按"上一条消息属于谁谁优先"轮换（开局左侧优先）。两窗消息不会并行冒出，一来一回。
- **章间"上下文重置中"仪式**（ChatPane 跨章检测 + clear-messages）：某窗下一拍与已播最后一拍跨章时，先盖半透明蒙版+转圈显示"上下文重置中…"（约2.2s），然后 clear-messages **真实清空该窗全部聊天记录**（约再留白2s后出新章消息）。已存记忆保留——清空后没存的高亮候选**永久消失**，这是阅后即焚的戏内落实；重载存档幂等（消息已空则不再重复仪式）。
